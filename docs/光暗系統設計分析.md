# 光暗系統設計分析

> 探討「光與暗」作為餘響玩法擴展方向的可行性、契合度、整合層次、美術成本與風險。
>
> 結論：**契合度極高、美術成本意外低、推薦先做純美術層的低成本驗證再決定是否擴展玩法**。

---

## 〇、TL;DR（速覽）

| 面向 | 評估 |
|---|---|
| **與餘響主題契合度** | ★★★★★（光已是既有視覺語言） |
| **美術成本（你的色塊風格下）** | 低（Light2D + CanvasModulate 內建、不需畫資產） |
| **設計成本** | 中（暗室調校需要時間） |
| **與 Recording 系統相容性** | ✓ 純視覺、不影響物理一致性 |
| **建議行動** | 先做 30 分鐘低成本驗證 → 看感覺再決定走哪一層 |

---

## 一、為何契合度高：光已是既有視覺語言

**核心理解**：你**並不是「加入新元素」、是「強化既有元素」**。

### 1.1 餘響已有的光暗語言盤點

| 既有元素 | 隱含的光/暗概念 |
|---|---|
| **LightPoint**（[LightPoint.tscn](../godot/scenes/LightPoint.tscn)）| 錄製起點留下的「光點」——BRIGHT / TRACE 兩態本質就是「亮 / 暗」 |
| **儀式 (recording ritual)** | PlayerController 用光點脈動標記錄製生命週期 |
| **殘骸 → 痕跡** | [PhysicalCarcass](../godot/scripts/PhysicalCarcass.gd) → [CarcassTrace](../godot/scenes/CarcassTrace.tscn) 灰色化即「亮活物 vs 暗痕跡」 |
| **詩意 / 靜謐基調** | [文案用語規劃.md](文案用語規劃.md) 確立的詩意風與「微光美學」天作之合 |
| **死亡黑屏** | [PlayerController](../godot/scripts/PlayerController.gd) 的死亡流程已用「光的消失」表達失敗 |
| **TitleScreen 背景 shader** | [TitleScreen.tscn](../godot/scenes/TitleScreen.tscn) 已用光暈作為視覺主題 |

### 1.2 核心隱喻已成立

> **「你的過去照亮你的現在」**

這就是錄製 / 重現分身的本質——光暗系統只是把這個**從象徵層下沉到玩法層**。

### 1.3 與其他主題擴展方向對比

| 主題 | 與餘響契合度 | 理由 |
|---|---|---|
| **光與暗** | ★★★★★ | 既有視覺語言的延伸、詩意、deterministic 友好 |
| **時間倒流** | ★★★ | 與「線性時間」設定衝突 |
| **重力翻轉** | ★ | 打掉錄製 / 重現假設 |
| **炸彈 / 爆破** | ★ | 不可逆性、暴力感衝突基調 |
| **武器戰鬥** | ✗ 不適用 | 完全衝突核心 |

光/暗是**少數幾乎沒有衝突點**的擴展方向。

---

## 二、整合層次（依投入由小到大）

### 層次 1：純美術強化（不改玩法）

**內容**：
- `CanvasModulate` 全場景偏暗（每個 area 用不同色調，呼應 [Room.area_color](../godot/scripts/Room.gd:12)）
- LightPoint 用真正的 `Light2D`、會在地板上灑光
- 玩家身上加微光（標示玩家位置）
- 分身（Clone）身上也有微光、顏色不同（區分過去）

**特性**：
- **成本**：3~5 小時、純視覺、不影響任何邏輯
- **效果**：氛圍 +60%、玩法 0% 變化
- **風險**：幾乎沒有
- **可逆**：不滿意可秒撤回

### 層次 2：暗室作為房間變體（玩法擴展）

**內容**：新增「**暗室**」房間類型：
- 整個房間 CanvasModulate 設為深暗（如 `Color(0.15, 0.15, 0.2)`）
- 玩家自身光照範圍**很小**（看不清遠處）
- **分身有自己的光照**（這是設計重點）

**核心解謎**：
> 「**過去的你」走過的路徑會被照亮、現在的你才能看到地形/陷阱**

**典型流程**：
1. 玩家盲走、死了、依稀記住地形
2. 錄一段「自己走某條路、把該路照亮」
3. 召喚分身重現 → 路被照亮 → 現在的你看清楚走過去

**特性**：
- **成本**：學 Light2D + Occluder ≈ 3~5 小時、加 1~2 個房間
- **與 Recording**：100% 相容（Light2D 是視覺，不改物理）
- **風險**：暗室調校不易、可能讓玩家挫敗

### 層次 3：光作為機關語言（玩法核心）

**內容**：新類型機關以光為主語：

| 機關 | 行為 | 餘響特色 |
|---|---|---|
| **光感應門** | 只在強光照射時開、無光則關 | 「過去的你照亮 → 現在的你穿過」 |
| **暗區照明（蠟燭）** | 玩家可點亮、光持續、不會自滅 | 與一次性錄製互補的「永久效果」 |
| **影子陷阱** | 光照不到的區域才會生成（碰到就死）| 反向使用——必須避免遮擋光 |
| **光的折射** | 光點路徑被牆擋、需要分身擋光導向 | 分身做為「光的載體」 |
| **光暈計時器** | 分身發光的時間限制 | 加緊張感 |

**特性**：
- **成本**：每個機關 1~3 小時、與層次 2 累加
- **與 Recording**：完美結合，沿用既有錄製、不需改 input
- **風險**：機制堆疊可能讓遊戲認知負擔過重

---

## 三、推薦方案

**先做層次 1 → 看感覺 → 再決定是否進層次 2**。

理由：
1. 層次 1 本來就在 [Tier A polish 計畫](Godot 工具與技巧分析.md) 內、不算額外投資
2. 層次 1 完成後若效果不對、撤回零成本
3. 層次 2 的暗室房間可作為新增第 5 / 6 個 demo 房間時的試水
4. 層次 3 屬於「demo 完成後 polish 階段」考慮——目前不該分心

## 四、demo_room5 暗室具體設計（層次 2 提案）

如果決定試層次 2，**用 1 個房間驗證概念**——demo_room5 試暗室。

### 4.1 房間骨架

```
demo_room5（暗室）
├── 入口（左下）：玩家進來、視野很小、看不到右邊
├── 路徑 A（上方）：要先看到才能跳
├── 路徑 B（下方）：全暗區、有 Hazard 隱藏
├── 出口（右上）
└── 關鍵：路徑 A 上有 LightPoint 投射、要分身踩過去把路徑 A 整段照亮
        現在的你才看得到怎麼跳
```

### 4.2 玩法流程

1. 玩家進房 → 全暗、只看得到 5 公尺內
2. 玩家亂走 → 掉進 Hazard 死 → 重生但記住「右下有東西」
3. 玩家錄一段「站著不動 5 秒、發出**持續性光暈**」（或「走到光點處」）
4. 召喚分身重現 → 分身在光點亮起 → 現在的你看清整個房間
5. 分身光照亮路徑 A → 你跳過去 → 通關

### 4.3 為什麼這個設計好

- **核心隱喻具象化**：「你的過去（分身）真的在照亮你的現在」
- **與既有 LightPoint 視覺語言一致**：BRIGHT 光點本來就是脈動發光的
- **Recording 0 改動**：純物理 + 視覺
- **Tier A 美術投資的最佳回收**：你做 Light2D 的工不會白費

### 4.4 關鍵調校參數

| 參數 | 建議起點 | 調校方向 |
|---|---|---|
| 暗區 CanvasModulate | `Color(0.15, 0.15, 0.2)` | 太黑 → 提到 0.25；太亮 → 降到 0.10 |
| 玩家光照半徑 | 200 px | 太小看不見路 → 提；太大失去「暗」感 → 降 |
| 分身光照半徑 | 300 px（比玩家強） | 強化「過去照亮現在」感受 |
| 光點靜態光半徑 | 250 px | 配合周遭可視範圍微調 |

## 五、美術成本分析

> 這是最關鍵的一節——回應「美術成本會不會暴增」的擔心。

### 5.1 光/暗系統的真正美術成本（拆解）

| 項目 | 是否需要美術資產 | 成本 |
|---|---|---|
| `CanvasModulate`（全場染色） | ❌ 純 Color 值 | 0 |
| `Light2D` 光源 | ❌ Godot 內建預設 gradient | 0 |
| `Occluder`（投影） | ❌ 重用既有 CollisionShape | 0 |
| 玩家身上微光 | ❌ Godot 內建 | 0 |
| 分身發光（Clone） | ❌ 改 Polygon 顏色 + 加 Light2D | 0 |
| LightPoint 真實發光 | ❌ Godot 內建 | 0 |
| 黑屏 / 暗區漸變 | ❌ ColorRect | 0 |

**核心理解**：光/暗的 80% 效果靠**程式化**而非美術資產。

### 5.2 會增加美術成本的東西（可以選擇不做）

| 進階項目 | 必要性 | 成本 |
|---|---|---|
| 自訂光形狀（非圓形）紋理 | ❌ 可選 | 10 分鐘 PS / Krita 畫一張 |
| 灰塵粒子紋理（光柱裡的塵） | ❌ 可選 | 5 分鐘或用 Godot 內建 |
| 「亮/暗」物件雙版本貼圖 | ❌ 不必（你是色塊風）| - |
| 細緻像素美術背景 | ❌ 不必 | - |
| 角色 sprite 動畫的明暗版本 | ❌ 不必（你目前是 Polygon）| - |

> 你目前**完全沒有像素美術資產**——所有東西都是 Polygon2D 色塊。**這反而讓你佔了便宜**：色塊在不同光照下「自動變色」（Light2D 直接改 modulate）、不用畫 5 個版本的 sprite。

### 5.3 與其他視覺方向的成本對比

| 方向 | 美術資產成本 | 視覺提升 | CP 值 |
|---|---|---|---|
| **光/暗 + Light2D** | **極低**（你目前風格） | 高 | ★★★★★ |
| GPUParticles（粒子）| 低（內建紋理夠用） | 中 | ★★★★ |
| Camera Shake | 0 | 低 | ★★★★ |
| Parallax 背景 | 中（要畫多層背景） | 中 | ★★★ |
| Pixel Art Tileset | **高** | 高 | ★★ |
| 角色 Sprite + 動畫 | **極高** | 中 | ★ |
| 自訂 Shader | 低（抄 GodotShaders.com） | 中~高 | ★★★ |

### 5.4 什麼情境光/暗才會變貴

3 種會讓光/暗暴增成本的決定，**你都不必做**：

| 決定 | 為什麼會變貴 | 避法 |
|---|---|---|
| 角色變成 sprite art | sprite 在不同光照下需要不同版本 / normal map | 保持 Polygon2D 色塊風（已是現狀） |
| 暗室裡放可讀的「文字 / 圖示」 | UI 元素在暗區得有發光版本 | 暗室不放 UI、只放幾何元素 |
| 真實感光影模擬（水反光、玻璃折射） | 需寫進階 shader | 保持風格化（單色光暈即可） |

## 六、低成本驗證方法（30 分鐘試）

不要直接做整個系統。先用 **30 分鐘**驗證：

### Step 1（5 分鐘）：開啟編輯器、加 CanvasModulate
1. 打開 [demo_room2.tscn](../godot/scenes/rooms/demo_room2.tscn)
2. 加一個 `CanvasModulate` 子節點、設 `Color(0.3, 0.3, 0.4)`
3. 跑遊戲看效果

### Step 2（10 分鐘）：給 Player 加 PointLight2D
1. 打開 [Player.tscn](../godot/scenes/Player.tscn)
2. 加 `PointLight2D` 子節點
3. 用 Godot 預設 light texture（不必畫）
4. 半徑 200 px、Energy 1.0
5. 跑遊戲看玩家身上是否有微光

### Step 3（10 分鐘）：給 LightPoint 加真實光照
1. 打開 [LightPoint.tscn](../godot/scenes/LightPoint.tscn)
2. 加 `PointLight2D` 子節點到 BRIGHT 狀態
3. 修改 [LightPoint.gd](../godot/scripts/LightPoint.gd) 的 `convert_to_trace()` 把 light 也淡掉

### Step 4（5 分鐘）：判斷
- 跑遊戲、走入 demo_room2 看感覺
- 召喚分身、看分身是否仍夠醒目
- 看 LightPoint 是否真的「在房間裡發光」

### 判斷準則
- **「喔！這就是餘響該長的樣子」** → 進入正式做（先層次 1、再決定要不要進層次 2）
- **「畫面太黑、看不清玩」** → 停手、回去做拉桿/彈簧
- **「氛圍變了但分不清玩家在哪」** → 玩家光半徑調大、或先別動 CanvasModulate

**這 30 分鐘的試錯比想像便宜**——3 步驟可逆、不影響其他系統。

## 七、風險點

| 風險 | 影響 | 解法 |
|---|---|---|
| **Light2D 影響 Recording 一致性** | 致命 | Light2D 只影響渲染、不影響物理。但需驗證跨 frame light 計算是否影響 hazard 判定 |
| **暗室太黑導致玩家挫敗** | 中 | 提供「最小可視範圍」（玩家身上自帶弱光、≥3 公尺） |
| **效能（多個 Light2D + Occluder）** | 中 | 1 房間 ≤ 5 個動態光源 |
| **視覺辨認度下降** | 中 | 互動物（按鈕、門）即使在暗區也保持自身發光 |
| **與 area_color 衝突** | 低 | CanvasModulate 與 area_color 用同色系、不互斥 |
| **過度黑暗破壞詩意基調** | 低~中 | 不要全場全黑、保持「微光」感（最低值 ≥ 0.10）|

## 八、結論與行動建議

### 8.1 立場
光/暗系統**對餘響是極高契合度的擴展方向**，且**美術成本對你的色塊原型風格出奇地低**。**用戶擔心的美術暴增問題在這個情境下不成立**。

### 8.2 行動順序

```
[現在] 機關優先：先做拉桿、彈簧、計時門（Tier S）
   ↓
[Tier A polish 階段] 30 分鐘驗證 → 決定走哪一層
   ↓
[層次 1] 純美術強化 → 評估視覺效果
   ↓
[層次 2] demo_room5 暗室試水 → 評估玩法可行性
   ↓
[層次 3] 光感應機關 → 已是後期 polish 階段才該考慮
```

### 8.3 不要做的事

- ❌ 為了光/暗系統開始畫像素美術
- ❌ 跳過層次 1 直接做層次 3
- ❌ 在 demo 玩法核心未驗證前花太多時間調光
- ❌ 把光/暗當成「拯救美術」的方法（它增強氛圍、不改基本玩法樂趣）

### 8.4 該做的事

- ✓ 把這份分析存著、Tier A polish 階段回來看
- ✓ 30 分鐘驗證實驗保留可逆性
- ✓ 先把核心機關（拉桿、彈簧）做完再來談視覺
