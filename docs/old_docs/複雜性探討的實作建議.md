## 二、技術決策（不變）

### 引擎
**Godot 4.6.2 Mono**（路徑：`F:/CCTEST/TOOL/Godot_v4.6.2-stable_mono_win64/`）。
已驗證：deterministic 物理、跳躍手感、輸入錄製重播。

### Determinism 折衷
- `CharacterBody2D` + 自寫 kinematic 移動，避開 RigidBody2D
- 所有移動邏輯放 `_physics_process`（固定 60Hz）
- `move_and_slide()` 短時間內穩定
- **驗收標準**：同一存檔 5 次召喚，最終位置誤差 < 5 px（M2 已通過）

### 碰撞層（M2.5 確立）

| Body | layer | mask |
|---|---|---|
| World StaticBody2D | 1 | 1 |
| Player | 1 | 3（World + Clone） |
| Clone | 2 | 1（World + Player，不偵測自己層） |

`platform_on_leave = 2`（DO_NOTHING）已加在 Player 與 Clone，避免站在跳躍中分身上時的不穩定起跳。

### 嚴格 typing
專案開「Warning Treated as Error」。所有變數推導要避開回傳 Variant 的函式：

| Variant 版（用了會錯） | float 版 | int 版 |
|---|---|---|
| `max()` | `maxf()` | `maxi()` |
| `min()` | `minf()` | `mini()` |
| `abs()` | `absf()` | `absi()` |
| `clamp()` | `clampf()` | `clampi()` |
| `lerp()` | `lerpf()` | — |

## 三、新 Roadmap（M4 起）

對應 [設計構想.md](設計構想.md) 的核心機制變更，重新規劃。

### M4 — 錄製儀式重做（本體留原地）

**目標**：把現在「玩家邊走邊錄」改成「按 R → 本體留原地、新分身出現、玩家操控分身」。

**為什麼先做這個**：這是設計主題的視覺核心。如果這個儀式做出來感覺不對（變成「分身術」而非「時間分裂」），整個敘事方向要重想。

**實作要點**：
- 按下 R → 在當前位置生成「Body Shadow」節點（半透明 Player 視覺、StaticBody2D，不參與召喚）
- 同時生成一個「Recording Clone」節點（從 Player.tscn 衍生，但是輸入來源是鍵盤）
- 把鏡頭與輸入控制權從 Player 切到 Recording Clone
- 結束錄製鍵 → Recording Clone 消失、Body Shadow 消失、玩家本體可動
- 此時光點還沒做（M5 才做），先用 print 印「光點生成於 X」

**修改檔案**：
- `Player.gd`：拆分「本體」與「錄製分身」邏輯，加 `is_recording_proxy` 變數
- `RecordingManager.gd`：管理 Body Shadow 與 Recording Clone 的生成與銷毀
- 新檔 `BodyShadow.tscn`：半透明本體佔位

**驗收**：按 R 後視覺有清楚的「分裂」感（不是「我變透明了」），錄製過程感覺像在控制另一個我，結束時感覺像「這次選擇結束了」。

### M5 — 光點系統

**目標**：每次結束錄製生成一個光點留在地圖上，玩家可走到光點上互動。

**實作要點**：
- 新檔 `LightPoint.tscn`：Area2D + 視覺（脈動的淡色光圈）
- 結束錄製時 → RecordingManager 在錄製起點生成 LightPoint，綁定 recording 資料
- 玩家走進 LightPoint 範圍 → 顯示互動提示（如「按 E 裝載」）
- M5 階段先簡單：按 E → 直接召喚該光點的分身
- M5 不做 hotbar，先驗證光點互動感

**修改檔案**：
- `LightPoint.gd`、`LightPoint.tscn`（新）
- `RecordingManager.gd`：管理光點清單
- `Player.gd`：偵測 LightPoint 並回應 E 鍵

**驗收**：地圖上能看到每個錄製過的位置都有光點，走到光點上能感覺到「這裡有東西」，按 E 能召喚對應分身。

### M6 — Hotbar（1-5 槽位）

**目標**：玩家最多有 5 個 hotbar 槽位，每個槽可裝載一個光點，按 1-5 召喚。

**實作要點**：
- 走到 LightPoint → 顯示槽位選單（5 格）
- 玩家選一個槽位 → 該光點被指派
- 按 1-5 → 從對應槽位的光點召喚分身
- 砍掉 CloneSpawner 原本的「按 1-9 召喚最近錄製」邏輯
- HUD 加 hotbar 顯示（5 個槽位、每格顯示對應光點縮略圖或編號）

**修改檔案**：
- `HotbarManager.gd`（新，autoload）
- `HUD.gd`、`HUD.tscn`：加 hotbar 顯示
- `LightPoint.gd`：加裝載互動
- `CloneSpawner.gd`：改成從 hotbar 讀

**驗收**：能裝載 5 個光點到槽位、按 1-5 各召喚不同分支、能切換槽位裝載新光點、舊光點仍存在地圖上但脫離 hotbar。

### M7 — 殘骸系統 + 5 視窗

**目標**：分身被機關殺死留殘骸、最近 5 個殘骸有實體、舊的變痕跡。

**實作要點**：
- 新檔 `Carcass.tscn`：StaticBody2D + 視覺（淡色定格剪影）+ 碰撞層配置（Player 可踩可壓）
- 新檔 `Hazard.tscn`：機關（如尖刺），偵測 Clone 進入時 emit signal
- Clone 被殺時 → RecordingManager 生成 Carcass 在死亡位置
- CarcassManager（autoload）維護一個最大 5 個的 FIFO 佇列：第 6 個進來時把最舊的 Carcass 切換為 Trace
- 新檔 `Trace.tscn`：純視覺、無碰撞、半透明的殘骸殘像

**修改檔案**：
- `CarcassManager.gd`、`Carcass.tscn`、`Trace.tscn`、`Hazard.tscn`（全新）
- `Clone.gd`：被機關殺時 emit died signal
- `PressButton.gd`：filter 加上 StaticBody2D（殘骸可壓）

**驗收**：分身踩尖刺死、留下殘骸；第 6 個分身死時最舊殘骸變痕跡；殘骸可踩可壓壓力板。

### M8 — 多分身互動 + 進階謎題元素

**目標**：能同時召喚多個分身、分身可疊高、玩家可踩分身。

**實作要點**：
- 多分身已可（M2 完成），但要驗證複雜場景下的時序穩定
- 加新的謎題元素：壓力板（持續觸發 vs 切換式）、移動平台、定時門
- 不加新核心機制，只加新型機關

**修改檔案**：各種新機關場景（按需建立）

### M9 — 第二、第三、第四個教學謎題

**目標**：根據 設計構想 的 Stage 1-5 教學進程，做出後續謎題群。

**實作要點**：
- Stage 2：光點 + Hotbar 教學謎題（分支 A 與 B 同時活躍）
- Stage 3：殘骸（被動犧牲）教學謎題
- Stage 4：殘骸視窗教學謎題
- Stage 5：多分身協作教學謎題

每個謎題都應該有專屬場景檔。

## 四、實作風險

### 風險 1：M4 視覺儀式重量不足
按 R 後如果視覺沒有「分裂」的力量感，整個主題的核心傳達失效。

**對策**：M4 結束時自己玩 5 分鐘，問自己「按 R 的瞬間我感覺到分裂了嗎」。沒感覺就花時間調視覺（時間靜止 0.5 秒、本體淡化動畫、分身浮現動畫），不要急著進 M5。

### 風險 2：Hotbar 互動流程繁瑣
「走到光點 → 開選單 → 選槽位 → 走開」這個流程在實際玩起來可能比想像中卡。

**對策**：M6 完成後自己玩，如果覺得「換 hotbar 是負擔」，考慮簡化（例如自動裝載最近錄製的 5 個）。

### 風險 3：殘骸視窗（5 個）的玩家認知
玩家可能不理解「為什麼這個殘骸變透明了」。

**對策**：第 6 個殘骸出現時，最舊那個有明顯的「淡化動畫」（過 1-2 秒從實體變痕跡），讓玩家看見變化過程。

### 風險 4：開發週期低估
新 roadmap M4-M9 估計 2-3 個月（業餘時間）。一週 10-20 小時的話，可能要更久。

**對策**：每完成一個 milestone 就誠實檢視時間花了多少，與計畫對比。如果某個 milestone 超過 2 週還沒完成，停下來問自己「是不是 scope 太大了」。

## 五、必須避開的陷阱

1. **過早做美術**：色塊撐到 Stage 3-4 教學謎題完成。機制不好玩，再漂亮都救不回來。
2. **追求 100% determinism**：原型階段「同一 Recording 召喚 5 次最終位置誤差 < 5 px」就夠了。
3. **跳過手感調校直接做機制**：M0 已過、別回頭動手感參數，除非試玩反饋出問題。
4. **加新核心機制**：每加一個都增加教學負擔。寧可挖深既有的。
5. **太早做存檔到磁碟**：原型階段全部 in-memory。等遊戲整體成型才做磁碟存檔。

## 六、驗收協議

### 每個 milestone 自驗
- 自己玩 10 分鐘，能否完成該階段的核心循環
- 是否有「啊哈」感（適用於需要頓悟的 milestone）
- 是否有任何 IDE 紅字、Output 警告

### 中期試玩（M7 完成後建議做）
- 找 1-2 個朋友試玩
- 不給任何提示，看他們能不能在 30 分鐘內理解核心機制
- 觀察哪裡卡住、哪裡有「啊哈」、哪裡放棄

### 大型試玩（M9 完成後）
- 找 5+ 個從沒看過遊戲的人試玩 1 小時
- 統計：能在 1 小時內走完前 3 個 Stage 的比例
- 如果 < 50%，重新檢視教學設計
