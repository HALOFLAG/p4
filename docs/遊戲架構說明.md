# 一、新舊架構對比（速覽）

## 1.1 舊架構（M0-M11 原始狀態）

**特徵**：
- World.tscn 一個檔 616 行，所有房間/物件 inline
- 每個按鈕、門、出口都是手刻 `Area2D + Polygon2D + CollisionShape2D` 三件套
- 機關參數（門開合時間、按鈕計次目標）寫死在 const
- 動畫用 `_physics_process` 手刻插值或 Tween 鏈
- 視覺單調（沒有 Light2D、沒有 Particle、沒有 CanvasModulate）

### ✅ 優點
| 點 | 說明 |
|---|---|
| **學習成本低** | 完全不用懂 @tool、scene inheritance、custom resource、AnimationPlayer |
| **一覽性強** | 打開 World.tscn 一個檔看完整個遊戲所有物件 |
| **除錯線性** | 沒跨檔，bug 通常一個檔內找得到 |
| **Godot 新手友好** | 標準新手做法，網路教學都這樣寫 |
| **小遊戲夠用** | 5~10 個房間、10 種機關以下，這樣寫沒問題 |

### ❌ 缺點
| 點 | 說明 |
|---|---|
| **重複代碼多** | 同樣的按鈕在 World.tscn 出現 6 次，每次 14 行 |
| **改一處要改多處** | 想換按鈕視覺顏色 → 6 個地方都得改 |
| **檔案肥大** | World.tscn 616 行；新增 1 個房間就 +100 行 |
| **編輯時不能預覽** | 改 sub_resource 大小要進 inspector 一個個改、看不到視覺 |
| **機關不能個別調整** | 全部同 `OPEN_TIME = 0.6`、做不出「快門 0.3s / 慢門 1.0s」的設計變化 |
| **分工困難** | 兩個人同時改 World.tscn 一定 git 衝突 |
| **加機關痛苦** | 要在已 600 行的檔內找位置塞、容易漏網 |

## 1.2 中間態（批次 A+B+C 完成後 = 目前狀態）

**已做的事**：
- 批次 A：建立 `components/` — 5 個可重用元件（PressButton、Door、Exit、Platform、HazardZone），每個有 `@tool` 即時預覽

- World.tscn 從 616 → 51 行

### ✅ 優點
| 點 | 說明 |
|---|---|
| **改一處全部同步** | 改 PressButton.tscn 視覺 → 所有按鈕統一更新 |
| **檔案專注** | 每個房間獨立檔、改 demo_room4 不會誤動其他房間 |
| **編輯器即時預覽** | 拖元件 → Inspector 改尺寸 → 視覺立刻同步 |

| **機關參數仍 const** | `OPEN_TIME = 0.6` 還寫死，沒做成 .tres |
| **視覺仍簡陋** | 沒 Light、沒 Particle、純色塊原型 |
| **沒持久化** | 玩家設定、進度、自製關卡都做不到 |

## 1.3 完整新架構（Tier S+A 都做完）

**還要加的事**：
- AnimationPlayer 取代手刻動畫（Tier S）
- Custom Resource 擴展：機關參數、房間 metadata、玩家手感都資料化（Tier S）
- Light2D + CanvasModulate + GPUParticles + Camera Shake + Parallax（Tier A 視覺）
- TileMap 處理重複地形（Tier A）
- ConfigFile + JSON 存讀檔（Tier A）

### ✅ 優點
| 點 | 說明 |
|---|---|
| **所有動畫集中視覺化** | 開啟 .tscn 點 AnimationPlayer 看 timeline、不用追 _physics_process |
| **設計師可獨立調機關** | 改 LeverConfig.tres → 不用改任何程式碼 |
| **整體美術提升** | 微光、粒子、視差、震動 = 從原型風變專業遊戲質感 |
| **新增房間極快** | TileMap 刷地形比手刻快 10 倍 |
| **可發行** | 設定持久化、存讀檔、可加 Translation、Steam 上架完備 |
| **錄製可分享** | Recording.tres 序列化、玩家可分享通關解 |
| **未來機關都套同模式** | 拉桿/彈簧/計時門按既定模板加，不必設計新架構 |

### ❌ 缺點
| 點 | 說明 |
|---|---|
| **學習成本高** | 要懂 @tool / scene inheritance / custom resource / AnimationPlayer / TileMap / Light2D 等 6+ 概念 |
| **檔案數爆增** | 從 1 個 World.tscn → 5 元件 + 5 房間 + N 個 .tres 配置檔 |
| **跨檔追 bug 困難** | 一個門的行為可能涉及 Door.gd、Door.tscn、AnimationPlayer、MechConfig.tres 多處 |
| **過度抽象風險** | 把「只用 1 次的設定」也做成 .tres = 純粹增加複雜度 |
| **Determinism 風險** | 換 AnimationPlayer 可能影響錄製重現一致性，需驗證 |
| **個人專案可能 over-engineering** | 對 100 房間、團隊 5 人專案才必要；3 房間個人專案 overkill |

## 1.5 取捨總結

### 什麼時候停在「目前狀態」最好？
- **個人專案、玩法定型**：你只想做完 5~6 房間的 demo，沒打算上 Steam → **目前架構足夠**，不必做 Tier S+A
- **時間有限**：剩下時間想做新機關/新房間 → 元件化已經幫你省 70% 時間，動畫先不重做也行
- **學習負擔已滿**：剛學 @tool + scene inheritance、需要消化 → 不要再疊新東西

### 什麼時候要做完 Tier S？
- **想做精緻 demo 給人看**：AnimationPlayer + 微光 + 粒子立刻提升 60% 質感
- **要新增 5+ 個機關**：每個都用 .tres 配置會比寫死 const 划算
- **遊戲玩法已穩定、進入美術 polish 階段**

### 什麼時候要做完 Tier S+A 全套？
- **打算上架**（Steam、itch.io）：i18n、存檔、設定持久化都是必備
- **想做關卡編輯器或玩家分享**：Replay Sharing + JSON levels 是基礎
- **計畫長期維護**（半年以上開發）：架構紅利會慢慢顯現

### ⚠️ 警告：避免過度工程
- 不要為了「未來可能需要」做抽象。需要時再做
- `.tres` 配置不要每個值都做、只做「設計師會調整 ≥3 次」的東西
- AnimationPlayer 不必每個物件都用，純色塊 Polygon 用 Tween 也夠

# 二、完整實作後的架構詳解

> 假設 Tier S+A 都做完後的完整架構長相。當下不必照單全收，但知道目標可以幫助每次做小改動時方向一致。

## 2.1 整體分層（6 層）

```
┌─────────────────────────────────────────────────────────┐
│  ① 輸入層     InputMap actions（move/jump/record/E）    │
└─────────────────┬───────────────────────────────────────┘
                  ▼
┌─────────────────────────────────────────────────────────┐
│  ② 控制層     Autoloads — 全域協調者                    │
│    PlayerController · RecordingManager · CarcassManager │
│    RoomManager     · AudioManager      · GameStats     │
└─────────────────┬───────────────────────────────────────┘
                  ▼
┌─────────────────────────────────────────────────────────┐
│  ③ 場景層     World.tscn = 骨架                          │
│    Player + HUD + 5 demo_roomN + DeathBand + Camera2D   │
└─────────────────┬───────────────────────────────────────┘
                  ▼
┌─────────────────────────────────────────────────────────┐
│  ④ 房間層     demo_roomN.tscn（繼承 Room.tscn）         │
│    TileMap 地形 + 元件實例 + 異形平台 + Sign + Checkpoint│
└─────────────────┬───────────────────────────────────────┘
                  ▼
┌─────────────────────────────────────────────────────────┐
│  ⑤ 元件層     scenes/components/*.tscn（@tool）         │
│    PressButton · Door · Exit · HazardZone · Platform   │
│    + 未來：Lever · Spring · TimedDoor · MovingPlatform │
└─────────────────┬───────────────────────────────────────┘
                  ▼
┌─────────────────────────────────────────────────────────┐
│  ⑥ 資料層     .tres / .json / user://                   │
│    MechConfig · LevelMeta · Recording · WalkConfig     │
│    settings.cfg · save.json                            │
└─────────────────────────────────────────────────────────┘
```

每層只跟相鄰層對話。**輸入流向下、事件流向上**（透過 signal）。

---

## 2.2 各層職責（誰管什麼）

### ① 輸入層
- `InputMap`：把實體按鍵抽象成動作名（`move_left`、`record`、`delete_slot`）
- 玩家可重綁鍵、自動支援手把
- **所有層都不直接讀鍵盤**，只認動作名

### ② 控制層（Autoloads）— 你已有，職責清楚
| Autoload | 主管 | 不該做的 |
|---|---|---|
| `PlayerController` | 錄製生命週期、傳送門選擇、地圖開關 | 不做物理移動（交給 Player） |
| `RecordingManager` | 5 槽 Recording 資料、FIFO、序列化 | 不管 Clone 生成 |
| `CarcassManager` | 殘骸生成/淡化/清理 | 不管按鈕邏輯 |
| `RoomManager` | 鏡頭跟隨當前房間 | 不管房間內物件 |
| `AudioManager` | SFX/BGM 播放、距離衰減、bus 控制 | 不管音樂選曲決策 |
| `GameStats` | 跑統計（死亡數、按鈕次數） | 不管 UI 顯示 |

### ③ 場景層（World.tscn — 骨架）
- 51 行的小檔，純粹組裝
- 連線 demo_roomN 的 button → door signal
- 換關卡只需改這一個檔的房間實例

### ④ 房間層（demo_roomN.tscn）
- **繼承** Room.tscn → 自動帶 Bounds + CameraTarget + area_color
- 用 **TileMap** 刷地形（地板/牆/重複平台）
- 用 **元件實例** 放互動物件（按鈕、門、出口）
- 異形地形（demo_room1 P2 那種）保留為 inline StaticBody2D
- 每房可配 `LevelMeta.tres`（房名、area_color、Sign 文字、預設 BGM）

### ⑤ 元件層（components/*.tscn）
- 每個元件 = 場景 + 腳本 + `@tool`
- Inspector 可調尺寸/顏色，編輯器即時預覽
- 動畫由各自 **AnimationPlayer** 控制（取代手刻 _physics_process）
- 機關參數從 `MechConfig.tres` 讀（不寫死 const）

### ⑥ 資料層（.tres + 持久化）
- **.tres**：可由 Inspector 編輯 + 自動序列化的「資料卡」
- **ConfigFile**：玩家設定（音量、控制鍵）→ `user://settings.cfg`
- **JSON 存檔**：進度、checkpoint → `user://save.json`
- **Recording.tres**：可分享通關錄影

## 2.3 一次完整錄製/重現的資料流

**情境：玩家在 demo_room2 錄製 → 召喚分身按鈕 → 門開 → 通過 → 觸發 Sign**

### Step 1：玩家按 LMB（錄製）
```
鍵盤"R" 
   → InputMap "record" action
   → Player.gd:_handle_special_actions() 偵測 just_pressed
   → PlayerController.start_recording(self)
```

### Step 2：PlayerController 啟動錄製儀式
```
PlayerController.start_recording()
   ├── Player.freeze()                       ← Player 凍結
   ├── RecordingManager.begin(slot_index)    ← 開資料容器
   ├── instantiate RecordingProxy            ← 偽裝玩家錄製
   ├── emit recording_started signal         ← 廣播
   │
   ├──→ World.gd 接到 → BGM ducking (-10dB)
   ├──→ AudioManager.play_sfx("record_start")
   └──→ GPUParticles2D 在玩家位置 emit 儀式星塵
```

### Step 3：錄製進行中
```
每幀（60 Hz）：
   RecordingProxy._physics_process(delta)
      ├── 讀 Input（與 Player 一樣）
      ├── _apply_movement() ← 共用 Player.gd 邏輯（Coyote/Buffer/Variable）
      ├── move_and_slide()
      └── RecordingManager.add_frame(left, right, jump)
   
   渲染：
      ├── Camera2D follow RecordingProxy
      ├── AnimationPlayer "ritual_glow" loop
      └── Light2D 跟隨（如有）
```

### Step 4：Proxy 走進 Button 範圍
```
PressButton._on_body_entered(proxy)
   → bodies_on = 1
   → emit pressed_changed(true)
       │
       └──→ World.gd 接收（demo_room2 的綁定）
            → Door.set_target(true)
                ├── AudioManager.play_sfx_at("door_open", door.position)
                │   └──（透過 RoomManager.contains 找位於哪房 → bus 衰減）
                └── AnimationPlayer.play("open")
                    ├── 0.0s: visual.position.y=0, scale.y=1
                    ├── 0.6s: visual.position.y=200, scale.y=0.001
                    └──（keyframe）collision.disabled = true
```

### Step 5：玩家按 R 結束錄製
```
PlayerController.end_recording()
   ├── RecordingProxy.queue_free()
   ├── Player.unfreeze()
   ├── instantiate LightPoint (BRIGHT) at start_position
   ├── RecordingManager 把 Recording.tres 寫入 slot
   └── emit recording_ended → BGM 回升
```

### Step 6：玩家按 RMB 重現分身
```
PlayerController.spawn_clone(slot_index)
   ├── load Recording.tres from RecordingManager
   ├── instantiate Clone with recording 資料
   └── Clone 從 LightPoint 位置淡入（AnimationPlayer "fade_in"）

Clone._physics_process（每幀）：
   ├── input_left/right/jump = recording.input_frames[current_frame]
   ├── _apply_movement() ← 同樣共用 Player 邏輯
   ├── move_and_slide()
   └── current_frame++
```

### Step 7：Clone 按按鈕、門開、玩家通過
```
（同 Step 4 的 chain，但驅動者是 Clone）

Player 通過 Door
   → Player 進入 Sign 的 Area2D
       → Sign._on_body_entered(player)
       → 檢查 player.is_in_group("player_real") 
       → AnimationPlayer.play("fade_in") → label.modulate.a 0→1
```

### Step 8：玩家走出房間 Bounds → 鏡頭切到下個房間
```
Player exit demo_room2.Bounds
   → Room._on_body_exited
   → RoomManager.player_exited_room(demo_room2)
   
Player enter demo_room3.Bounds
   → RoomManager.player_entered_room(demo_room3)
   → Tween Camera2D.position → demo_room3.CameraTarget
   → Tween CanvasModulate.color → demo_room3.area_color
   → Parallax background 跟著飄
```

## 2.4 三種主要互動模式

### 模式 1：Signal 驅動（事件廣播）— 你已大量使用
**規則**：物件不知道誰在聽，只發 signal。其他人訂閱。

```
PressButton --pressed_changed--> Door.set_target
Player --died--> PlayerController.handle_death  
Checkpoint --touched--> PressCounter.reset
Recording --frame_added--> HUD.update_progress_bar
```

**優點**：物件解耦、可加新訂閱者不改舊程式
**陷阱**：訂閱亂連會變蜘蛛網。建議：**signal 連線寫在「擁有兩端的父節點」**（如 World.gd 連 button↔door，而非按鈕直接連門）。

### 模式 2：Resource 驅動（資料配置）— 待擴展
**規則**：行為寫在腳本、參數寫在 `.tres`。

```
LeverConfig.tres ──load──> Lever.gd 讀取 initial_state / sfx
LevelMeta.tres   ──@export─> demo_room2.tscn 配置 area_color/sign_text  
WalkConfig.tres  ──load──> Player.gd 套用 max_speed/jump_velocity
```

**優點**：改數值不用 commit code、可批次切換配置（normal/hard mode）
**陷阱**：過度抽象會讓追 bug 變難。**只把「設計師會調整」的東西放 .tres**。

### 模式 3：Scene Inheritance（場景繼承）— 你已用
**規則**：通用結構放父場景，子場景繼承後 override。

```
Room.tscn (Bounds, CameraTarget, area_color)
   ├── demo_room1.tscn ← 繼承 + 加自己的地形/物件
   ├── demo_room2.tscn ← 同上
   └── ...
```

**優點**：改 Room.tscn → 所有子場景同步更新
**陷阱**：override 太多會讓子場景混亂。**只繼承純結構、行為寫在腳本**。

## 2.5 新增一個機關（如「彈簧 Spring」）會碰到哪些層

具體看每層要做什麼：

| 層 | 要做的事 |
|---|---|
| ⑥ 資料層 | 建 `SpringConfig.tres`，定義 `bounce_velocity`、`sfx`、`color` |
| ⑤ 元件層 | 建 `Spring.gd`（@tool）+ `Spring.tscn`，含 AnimationPlayer 壓縮回彈動畫 |
| ⑤ 元件層 | 在 Spring.gd 加 `apply_bounce()` 處理玩家落上時的速度修改 |
| ④ 房間層 | 把 Spring.tscn 拖進 demo_room5.tscn（如果你做的話）|
| ③ 場景層 | 不需動 |
| ② 控制層 | 不需動（Spring 是局部互動，不需 autoload 協調）|
| ① 輸入層 | 不需動（玩家落上自動觸發，無需新 action）|

**結論**：新增一個無狀態機關 = 改兩層、不到 1 小時。

對比若是「拉桿 Lever」（有 toggle 狀態）：
- 多一層：可能要 emit `state_changed` signal、由 World.gd（或 demo_roomN 自己的 script）連到 Door.set_target
- 仍然 1~2 小時

---

## 2.6 跨層合作的「黃金路徑」

當你問「這個邏輯該寫哪一層？」，依這順序判斷：

1. **這是物件自己內部的事？** → 元件層（如 Door 開合動畫）
2. **這是兩個物件互動？** → 由「擁有兩者的父節點」連 signal（如 World.gd 連 button↔door）
3. **這是跨房間/全域事件？** → Autoload（如 PlayerController 處理錄製）
4. **這是純資料、設計師會改？** → .tres
5. **這是玩家設定，要持久？** → ConfigFile / JSON
