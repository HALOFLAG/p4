## 1. 錄製與結束錄製 — 主題契合度與實作分析

*分析日期：2026-05-01*
*對應設計：[`設計構想.md`](設計構想.md) 第三節 1+2*

兩階段對照「**和另一個版本的自己合作**」這個核心，要傳達的內在情感是：

- 錄製進入 = **「我分裂成兩個」的瞬間**
- 錄製過程 = **「我替自己選一條路」**
- 結束錄製 = **「這條時間線完成了」**

### 1.1 錄製階段的主題契合度

#### 應該傳達的情感

| 內在情感 | 設計如何嘗試表達 |
|---|---|
| 「我分裂了」 | 本體留原地、新分身浮現 |
| 「兩個我同時存在」 | 玩家視覺上看到兩個身影 |
| 「我控制的是岔出去的時間線」 | 鏡頭跟分身、本體靜止半透明 |
| 「這是不同的時間」 | 紅框／膠卷邊框視覺 |

#### 設計能做到嗎？

**可以，但取決於執行細節**。文字描述沒問題，但**機制本身傳達主題的能力是有限的**——關鍵在視覺儀式的「重量」。

##### 會傳達好的情況
- 按 R 後**世界明顯停頓**（0.3-0.5 秒）
- 本體**淡化過程可見**（不是瞬間切換）
- 分身**從本體位置「分離」出來**（短暫的疊影 → 偏移）
- 紅框邊框**從外緣淡入**而非瞬間出現
- 鏡頭轉移有**微妙過渡**（不要硬切）

##### 會搞砸的情況
- 按 R 瞬間：本體變透明、分身瞬間出現、紅框瞬間出現——**讀起來像「我穿牆了」或「我用了道具」**，不是時間分裂
- 分身與本體**完全重疊**地出現：玩家看到的是「我變透明了，怎麼還能動？」而不是「兩個我」
- 沒有「停頓」：按下 R 直接無縫繼續，**錯失「儀式感」的時機**

#### 真正的風險：玩家會用熟悉的概念詮釋陌生視覺

「時間分岔」是抽象哲學概念，**沒有任何視覺直接傳達它**。最終玩家如何詮釋取決於：
- 視覺儀式的重量
- 環境氛圍（音效、留白、留意細節）
- 文字標題與環境敘事

**機制即主題**這個目標**只能達成 60-70%**。剩下的 30-40% 必須靠視覺與敘事。

#### 主題裂縫的具體位置

| 裂縫 | 玩家可能的誤讀 |
|---|---|
| 本體留原地 | 「我把替身留下、自己跑去做別的事」（≈ 火影分身術） |
| 分身重現動作 | 「我有錄影回放功能」（≈ Cursor*10） |
| 殘骸 | 「我的分身死了」（不容易想到「另一個版本的我死了」） |
| 多分身共存 | 「我召喚了好幾個複製品」（≈ 寶可夢） |

**這些裂縫不是 bug，是主題傳達的物理極限**。可以靠視聽強化但無法消除。

### 1.2 結束錄製階段的主題契合度

#### 應該傳達的情感

| 內在情感 | 設計如何嘗試表達 |
|---|---|
| 「這條時間線完成了」 | 分身停止、消失 |
| 「主時間線回來了」 | 本體變回實體、控制回到本體 |
| 「這個選擇被刻入世界」 | 光點生成 |
| 「另一條時間線存在過」 | 槽位裡有了內容 |

#### 設計能做到嗎？

**比錄製階段更弱**。結束錄製是「儀式的退場」，玩家容易把它當作「把工具收起來」而非「完成一條時間線」。

#### 主題在這裡的具體挑戰

##### 「分身消失」 vs 「分身的時間線收束」
- 如果分身就「啪」一下消失：玩家解讀為「啟動結束、工具收起來」
- 如果分身「定格 → 淡化 → 散成光點 → 飄向上方」：玩家解讀為「**這個版本的我把選擇做完了，結束了**」
- 差異在動畫的時間（0.1 秒 vs 1.5 秒）與視覺修辭（瞬移 vs 散粒子）

##### 「本體變回實體」 vs 「我又是一個人了」
- 如果本體瞬間變不透明：感覺像 UI 切換
- 如果本體**從半透明緩慢變實**（0.5-1 秒）：感覺像「**這條時間線還給我了**」

##### 光點生成的時機
- 如果光點在分身消失「同時」出現：感覺像「我留下了個遺物」
- 如果光點在分身完全消失**之後**才慢慢浮現：感覺像「**這個位置現在記得發生過什麼**」

#### 主題裂縫的具體位置

| 裂縫 | 玩家可能的誤讀 |
|---|---|
| 分身瞬間消失 | 「錄製結束了」（功能性） |
| 結束鍵的命名 | 玩家會在腦裡叫它什麼？「停止錄製」「取消」？ |
| 光點作為「記憶」 | 玩家可能只當「召喚錨點」（操作工具），不感受「世界記得」 |

### 1.3 架構級實作挑戰：誰在什麼時候讀輸入

這是**最根本的實作難題**。

#### 三種狀態的輸入路由

| 狀態 | 鍵盤輸入給誰 | 誰在錄製 | 誰在播放 |
|---|---|---|---|
| 正常遊蕩 | Player（本體） | 無 | 無（除非有召喚的分身） |
| 錄製中 | Recording Clone（玩家暫時控制的分身） | RecordingManager（記下 RC 的輸入） | 召喚的舊分身仍在播放（如果有） |
| 召喚中（無錄製） | Player（本體） | 無 | 各 Clone 從錄製資料讀 |

#### 架構決策：兩條路線

**路線 A：Player 一個類別，多狀態 flag**

```
Player：
  - 狀態 NORMAL：讀鍵盤、移動、可錄製
  - 狀態 BODY_FROZEN：不讀鍵盤、不移動、半透明
  - 狀態 RECORDING_PROXY：讀鍵盤、移動、把輸入交給 RecordingManager
```

按 R：原本 NORMAL 的 Player 變成 BODY_FROZEN，新建一個 RECORDING_PROXY 的 Player。

**優點**：少一個類別。
**缺點**：Player 類別承載 3 種角色，單一責任原則違反。狀態切換邏輯複雜。

**路線 B（推薦）：拆出 RecordingProxy 類別**

```
Player：本體，可凍結
RecordingProxy（extends Player）：錄製中的可控分身，輸入會被記下
Clone（extends Player）：播放錄製的分身（已存在）
```

按 R：Player 凍結，新建 RecordingProxy，鍵盤輸入路由給它。

**優點**：
- 每個類別職責單一
- 沿用現有 Clone extends Player 的繼承鏈
- 現有 Player.gd 的 `_read_inputs()` 虛擬方法**已經支援**這個架構

**缺點**：多一個類別。

**推薦理由**：
- 凍結邏輯只需在 Player.gd 加一個 `is_frozen` flag，`_physics_process` 早退
- 與現有 Clone.gd 的設計一致

#### 控制權轉移的具體機制

```gdscript
# Player.gd 新增
var is_frozen := false

func _physics_process(delta):
    if is_frozen:
        return  # 不動、不讀輸入、不錄製
    # ... 原有邏輯

# RecordingProxy.gd（新）
extends Player
class_name RecordingProxy

func _ready():
    # 不加入 player_real group（這不是真本體）
    spawn_position = position
    visual.color = Color(0.4, 0.7, 1.0, 0.7)
```

按 R 時的流程（在 PlayerController 裡）：

```gdscript
func start_recording():
    var player = get_player()
    player.is_frozen = true
    player.modulate.a = 0.5  # 半透明
    
    var proxy = RECORDING_PROXY_SCENE.instantiate()
    proxy.position = player.position
    get_parent().add_child(proxy)
    
    RecordingManager.start_recording(player.position)
    set_camera_target(proxy)

func end_recording():
    var rec = RecordingManager.stop_recording()
    var proxy = get_recording_proxy()
    proxy.queue_free()
    
    var player = get_player()
    player.is_frozen = false
    player.modulate.a = 1.0
    set_camera_target(player)
    
    spawn_light_point(rec.spawn_position, slot_assigned)
```

#### 困難點：誰是「controller」

上述 `start_recording / end_recording` 應該掛在哪個節點？選項：
- RecordingManager（autoload）：但它是純資料管理，不應碰場景節點
- 場景根（FirstPuzzle.gd / Main.gd）：場景特定的，每個場景都要重做
- 新增一個 PlayerController autoload：管 Player 與相關場景物件

**推薦**：新增 `PlayerController.gd`（autoload 或 場景內的單例 Node），統一管控本體、proxy、camera、light point 的協調。

### 1.4 視覺儀式的時間軸（最考驗品質）

主題能否傳達 30-40% 取決於這部分。

#### 進入錄製的儀式時間軸

| 時間 | 事件 |
|---|---|
| 0.0s | 玩家按 R |
| 0.0s | 整個世界靜止（`Engine.time_scale = 0` 或 `get_tree().paused = true`） |
| 0.0~0.3s | 暫停期間：本體輪廓微閃白、開始淡化 |
| 0.3s | 暫停解除、新分身在本體位置淡入並略向側偏移（30 px） |
| 0.3~0.6s | 本體繼續淡化到 50% 透明、分身淡入到 100% |
| 0.3s | 紅框 / 膠卷邊框淡入 |
| 0.6s | 鏡頭從本體切到分身（用 0.3s 平滑過渡） |
| 0.9s | 玩家恢復控制、開始錄製輸入 |

**總儀式時長：0.9 秒**——比一般動作慢 3 倍，這是設計意圖（讓玩家感受重量）。

#### 結束錄製的儀式時間軸

| 時間 | 事件 |
|---|---|
| 0.0s | 玩家按結束鍵 |
| 0.0s | 分身停止、最後輸入記錄 |
| 0.0~0.3s | 分身定格、輪廓變亮 |
| 0.3~0.8s | 分身散成光點、向上飄、淡化 |
| 0.4~0.7s | 本體從 50% 透明過渡到 100%（早於分身完全消失，視覺重疊） |
| 0.4~0.7s | 紅框邊框淡出 |
| 0.5~0.8s | 鏡頭從分身位置回到本體位置（平滑過渡） |
| 0.8s | 光點在錄製起點淡入 |
| 1.0s | 玩家恢復對本體的控制、儀式結束 |

**總儀式時長：1.0 秒**。

#### 實作技術

- 世界靜止：`get_tree().paused = true` + 標記 PlayerController 為 `process_mode = ALWAYS`
- 各種淡化：Tween + tween_property
- 鏡頭過渡：Camera2D 的 `position_smoothing_enabled` 或手動 tween
- 紅框：CanvasLayer + ColorRect + 邊框樣式

**所有都是 Godot 標準操作**，但需要精準的時序協調。建議用一個 `RitualPlayer.gd` 統一管理時間軸，避免分散在多個檔案造成維護惡夢。

### 1.5 邊界情況與棘手細節

#### 1.5.1 本體位置在錄製中的處理

**問題**：本體凍結後，物理還在嗎？

| 選項 | 後果 |
|---|---|
| A. 完全凍結（StaticBody-like）：不受重力、不被推擠 | 推薦 |
| B. 視覺凍結但物理仍存在：可能被掉下來的東西壓死 | 體驗差 |

**推薦 A**——凍結期間本體無敵、無物理。否則玩家會在錄製中失去本體，體驗極差。

實作：`is_frozen=true` 時 `_physics_process` 早退；CollisionShape disabled 或 collision_layer=0。

#### 1.5.2 在空中按 R

**問題**：本體在空中，凍結後懸浮？

| 選項 | 評估 |
|---|---|
| A. 本體懸浮在空中（視覺奇怪但允許） | 推薦 |
| B. 限制只能在地面按 R（增加限制） | 過度限制 |

**推薦 A**——不要限制。玩家在空中需要錄製是合理的（例如錄一個跳躍動作）。「懸浮的本體影子」可以詮釋為「**時間在那裡停住了**」，反而強化主題。

#### 1.5.3 錄製中按 R 又按 R

設計已說「錄製中不能召喚」——但**錄製中可以按 R 嗎**？

| 選項 | 評估 |
|---|---|
| A. 忽略（最簡單） | 推薦 |
| B. 結束錄製（雙鍵當作 toggle） | 與結束鍵職責重複 |

**推薦 A**——按 R 在錄製中無效。結束鍵獨立。

#### 1.5.4 錄製中按結束鍵但沒實際做動作

**問題**：玩家按 R → 立刻按結束鍵，0.0 秒的錄製。

| 選項 | 評估 |
|---|---|
| A. 接受，存成 0 frame 的錄製（召喚出來什麼都不做） | 垃圾錄製佔槽位 |
| B. 忽略，當作沒錄 | OK |
| C. 設一個最短時長（如 0.5 秒），低於不存 | **推薦** |

**推薦 C**：低於 0.5 秒當作取消，不存槽位、不創光點。

#### 1.5.5 錄製中召喚的舊分身

設計已說「錄製中不能召喚」。但**已經召喚的分身怎麼辦**？玩家按 R 前已召喚分身 X，正在播放——

| 選項 | 評估 |
|---|---|
| A. 凍結所有正在播放的分身（時間真的停了） | 主題滿分，實作複雜 |
| B. 已召喚的分身繼續播放（時間沒停，只是切換控制權） | 簡單，主題稍弱 |
| C. 已召喚的分身全部消失（清場） | 玩家規劃被打斷 |

**推薦**：原型先用 B（簡單）、後期改 A（更主題）。

#### 1.5.6 視覺：本體與分身完全重疊的瞬間

按 R 那一瞬間，本體在位置 P，分身在位置 P。玩家看到的是「一個人」還是「兩個重疊」？

**對策**：分身淡入時略往側邊偏移（如 +30 px），形成「**從一個變成兩個**」的視覺修辭。
偏移後分身才離開本體位置，玩家移動分身時才不會有「我沒動我怎麼動了」的錯亂。

### 1.6 主題重量的「最低投資」

如果不做完整 1.0 秒儀式，**最低能接受的版本**：

#### 進入錄製
- 暫停 0.2 秒
- 本體淡化（modulate tween 0.3 秒）
- 分身淡入 + 側偏移 30 px（0.3 秒）
- 紅框淡入（0.3 秒）
- 鏡頭瞬切（不平滑過渡）

#### 結束錄製
- 分身淡出（modulate tween 0.4 秒）
- 本體淡入回實體（0.3 秒）
- 光點淡入（0.5 秒）
- 鏡頭瞬切

**省略**：時間軸的精確協調、平滑鏡頭過渡、定格 0.3 秒的儀式停頓。

工作量估計：M4 第一週做基本機制、第二週做最低儀式、之後可選打磨。

**警告**：**儀式時間如果短於 0.3 秒，主題就斷了**。寧可慢一點，不要快到沒重量。

### 1.7 總結

#### 主題契合度

| 階段 | 契合度（不含視覺儀式） | 含視覺儀式後可達 |
|---|---|---|
| 進入錄製 | 50% | 70-80% |
| 錄製過程 | 60% | 70% |
| 結束錄製 | 40% | 65% |

**結論**：**本體留原地 + 操控新分身**這個機制本身已經做了一半工作。剩下一半完全靠視覺儀式的執行品質。

#### 實作難度

| 項目 | 難度 |
|---|---|
| RecordingProxy 類別 + Player 凍結 | ★★（中低，沿用現有架構） |
| Camera 切換 | ★★（中低，標準 Godot 操作） |
| 視覺儀式時間軸協調 | ★★★★（中高，需 RitualPlayer 統籌） |
| 紅框 / 暫停 / 淡入淡出 | ★★（中低，Tween 操作） |
| 邊界情況處理（凍結期間無敵、空中錄製等） | ★★（中低，flag-based） |
| **整體** | **★★★ 中等** |

#### 主要風險

1. **視覺儀式做得不夠重**：主題斷掉，玩家把它當「分身術」
2. **RecordingProxy 與 Player 的責任界線模糊**：邏輯散落、未來難維護
3. **狀態管理沒有單一來源**：多個節點各自判斷「現在是不是錄製中」，bug 溫床

#### 建議的實作順序

1. **第一步：先做最低儀式版本**（M4 兩週工作量），自己玩，問自己「我感受到時間分裂了嗎」
2. **如果感受不到**，**先打磨儀式而非加機制**
3. **架構先定** PlayerController + RecordingProxy + RitualPlayer 三個職責，避免日後重構
4. **空中錄製、凍結無敵、錄製中其他分身怎麼處理**這幾個邊界先決定，寫進 [`設計構想.md`](設計構想.md) 第八節「待後期決定」清掉

#### 待寫進設計構想.md 的決策（如使用者確認）

- 凍結期間本體無敵、無物理碰撞
- 空中可錄製、本體懸浮停在空中
- 錄製中按 R 無效（結束鍵獨立）
- 最短錄製 0.5 秒，低於則不儲存（取消）
- 錄製中已召喚的舊分身：原型階段繼續播放（B），後期改成全凍結（A）
- 分身淡入時側偏移 30 px，避免與本體完全重疊

## 2. 殘骸 — 主題契合度與實作分析

*分析日期：2026-05-01*
*對應設計：[`設計構想.md`](設計構想.md) 第三節 4*

### 2.1 主題契合度

殘骸的核心情感：「**這條時間線走到死路**」「**我為了過關讓另一個版本的我死了**」。

#### 應該傳達的情感

| 內在情感 | 設計如何嘗試表達 |
|---|---|
| 「分身死了」 | 物理殘骸（定格剪影） |
| 「失敗的可能性也是世界的一部分」 | 殘骸是物理實體可互動 |
| 「最近的失敗 vs 久遠的失敗」 | 新／舊兩種痕跡樣式 |
| 「世界永遠記得」 | 痕跡無上限、永不消失 |
| 「主動犧牲是有重量的決定」 | 每次犧牲就是失去一個槽位的「物理殘骸權」 |

#### 主題裂縫

| 裂縫 | 玩家可能的誤讀 |
|---|---|
| 物理殘骸 vs 痕跡 | 「能用的殘骸 vs 不能用的殘骸」（功能性，主題弱） |
| 槽位制覆蓋 | 「最新覆蓋舊的」（資源管理，主題弱） |
| 主動犧牲 | 「策略性資源消耗」（取代「失去另一個版本的我」的情感） |

**主題傳達很大程度依賴視覺品質**——殘骸動畫、痕跡淡化、新舊樣式對比。
若做得有重量：玩家感受到「失去」。
若做得粗糙：玩家感受到「我又犧牲一個工具人」。

### 2.2 槽位制實作架構

#### 物理殘骸資料結構

```gdscript
class_name PhysicalCarcass extends StaticBody2D

var slot_index: int  # 0-4 對應 1-5 槽位
var death_position: Vector2
var formation_time: float

func _ready():
    add_to_group("physical_carcass")
    # 設定 collision_layer 讓玩家可踩、按鈕可偵測

func convert_to_trace() -> CarcassTrace:
    var trace = TRACE_SCENE.instantiate()
    trace.position = position
    trace.formation_time = formation_time
    get_parent().add_child(trace)
    queue_free()
    return trace
```

#### 痕跡資料結構（含新／舊兩階段）

```gdscript
class_name CarcassTrace extends Node2D

const NEW_DURATION := 60.0  # 60 秒內為「新」
const TRANSITION_TIME := 5.0  # 新→舊淡化過渡 5 秒

var formation_time: float
var is_new: bool = true

@onready var visual: Polygon2D = $Visual

func _ready():
    visual.modulate.a = 0.5  # 新痕跡 50% 亮度
    # 完全無物理：不加 collision

func _process(delta):
    if is_new and (Time.get_ticks_msec() / 1000.0) - formation_time > NEW_DURATION:
        is_new = false
        # 過渡到舊痕跡視覺
        var tween = create_tween()
        tween.tween_property(visual, "modulate:a", 0.2, TRANSITION_TIME)
```

#### CarcassManager（autoload）

```gdscript
extends Node

# 每槽位最多 1 個物理殘骸
var slot_carcasses: Dictionary = {}  # {slot_index: PhysicalCarcass}

func register_death(slot_index: int, position: Vector2, parent: Node):
    # 同槽位有舊物理殘骸 → 轉痕跡
    if slot_carcasses.has(slot_index):
        slot_carcasses[slot_index].convert_to_trace()
    
    # 生成新物理殘骸
    var carcass = PHYSICAL_CARCASS_SCENE.instantiate()
    carcass.position = position
    carcass.slot_index = slot_index
    carcass.formation_time = Time.get_ticks_msec() / 1000.0
    parent.add_child(carcass)
    slot_carcasses[slot_index] = carcass

func clear_slot_carcass(slot_index: int):
    # 槽位刪除/重錄/FIFO 時呼叫
    if slot_carcasses.has(slot_index):
        slot_carcasses[slot_index].convert_to_trace()
        slot_carcasses.erase(slot_index)

func reset_zone(zone: TriggerZone):
    # 本體死亡時呼叫
    var keys_to_erase = []
    for slot_idx in slot_carcasses.keys():
        var carcass = slot_carcasses[slot_idx]
        if zone.contains(carcass.position):
            carcass.convert_to_trace()
            keys_to_erase.append(slot_idx)
    for key in keys_to_erase:
        slot_carcasses.erase(key)
```

### 2.3 邊界情況的場景演練

#### 場景 1：同槽位反覆死亡（同位置）
- 召喚槽位 1，Clone 死於 P → 物理 A 在 P
- 再召喚 → Clone 同樣死於 P → 物理 B 在 P，A 轉痕跡
- 視覺：B 蓋在 A 痕跡上（玩家只看到 1 個物理殘骸）

#### 場景 2：跨槽位、相同位置死亡
- 槽位 1 Clone 死於 P → 物理 A（slot 1）
- 槽位 2 Clone 死於 P → 物理 B（slot 2），A 不轉痕跡
- 兩個物理殘骸並存於 P

#### 場景 3：本體死亡重置
- 玩家在 zone Z 內死亡
- zone Z 內所有物理殘骸 → 痕跡（不論屬於哪個槽位）
- 跨 zone 殘骸不變
- 槽位編號未變（錄製仍在）

#### 場景 4：玩家手動刪除槽位 1（Q 鍵）
- 槽位 1 錄製清空、亮光點消失
- 槽位 1 物理殘骸 → 痕跡（與 FIFO 一致）

#### 場景 5：玩家重錄槽位 1
- 舊錄製被取代
- 舊物理殘骸 → 痕跡
- 新錄製可形成新物理殘骸

#### 場景 6：FIFO 自動覆蓋
- 槽位 1 被 FIFO（其他位置新錄製把 1 擠掉）
- 槽位 1 物理殘骸 → 痕跡

#### 場景 7：多次同時召喚同一槽位
- 槽位 1 召喚 1 + 召喚 2 同時在場（兩個 Clone）
- Clone A 先死 → 物理 A
- Clone B 後死 → 物理 B，A 轉痕跡

#### 場景 8：RecordingProxy 死亡（決策 A3）
- RecordingProxy 撞機關死於 P
- 錄製存到槽位 N（含死亡 frame）
- 槽位 N 形成第一個物理殘骸於 P
- 之後召喚此錄製，會在同位置再死，形成新物理（覆蓋之前的轉痕跡）

#### 場景 9：痕跡跨 60 秒新舊轉換
- 物理殘骸轉痕跡 → 新痕跡狀態（50% 亮度）
- 60 秒後 → 開始 5 秒淡化過渡
- 65 秒後 → 完全進入舊痕跡狀態（20% 亮度）
- 之後永久保持 20% 亮度，不再變化

### 2.4 視覺實作要點

#### 物理殘骸 → 新痕跡的轉換動畫

| 時間 | 事件 |
|---|---|
| 0.0s | 觸發轉換（物理殘骸最後一次強光） |
| 0.0~0.5s | 物理殘骸淡化（modulate.a 100% → 50%）、邊緣光暈消散 |
| 0.5s | 開始 trace 模式（physics disabled、modulate 50%、無物理屬性） |
| 0.5s 起 | 60 秒倒數，到時間轉舊痕跡 |

#### 新痕跡 → 舊痕跡的轉換動畫

| 時間 | 事件 |
|---|---|
| 0.0s（formation_time + 60s） | 觸發轉換 |
| 0.0~5.0s | modulate.a 從 50% → 20%（緩慢淡化）、輪廓變模糊 |
| 5.0s 起 | 維持舊痕跡狀態，永不變化 |

### 2.5 實作難度評估

| 項目 | 難度 |
|---|---|
| PhysicalCarcass / CarcassTrace 場景 | ★★（中低，標準 Godot 場景） |
| CarcassManager autoload | ★★（中低，狀態管理） |
| 槽位事件的 hook（FIFO/重錄/刪除/死亡） | ★★★（中，多事件源需協調） |
| 新／舊痕跡的視覺差異與轉換 | ★★★（中，Tween + 美術配合） |
| 跨 zone 重置邏輯 | ★★★（中，需 trigger zone 系統） |
| 邊界情況覆蓋 | ★★（中低，flag-based） |
| **整體** | **★★★ 中等** |

### 2.6 主要風險

1. **新／舊痕跡的視覺差異不明顯**：玩家分不出 → 主題的「時間層次感」失效
2. **槽位事件的 hook 散落**：多個觸發點都要記得呼叫 `CarcassManager.clear_slot_carcass()`，少一處就 bug
3. **跨 zone 物理殘骸的累積**：玩家解過 5 個謎題後可能有 5 個物理殘骸散落不同位置——若位置湊巧影響後期謎題會混亂
4. **痕跡無上限的記憶體成本**：玩到後期可能有 100+ 痕跡。原型階段不擔心，但若實際撐不住需加全域上限

### 2.7 已確認的設計決策清單（已寫入 設計構想.md）

- ✅ 取消「玩家離開 zone N 秒後物理殘骸淡化」規則
- ✅ 改採槽位制：每槽位最多 1 個物理殘骸
- ✅ RecordingProxy 死亡 = 錄製儲存 + 形成物理殘骸（A3）
- ✅ 痕跡兩種樣式：新（50% 亮度，60 秒內）、舊（20% 亮度，60 秒後）
- ✅ 新→舊過渡時長 5 秒
- ✅ 痕跡無上限、永不消失
- ✅ 物理殘骸全域上限 = 5（每槽位 1 個）
- ✅ 跨槽位同位置物理殘骸並存
- ✅ 本體死亡重置範圍：當前 zone 內物理殘骸 → 痕跡（保留 B4 決策）
- ✅ 機關摧毀殘骸：後期可選（耐久性／時效性）
- ✅ 痕跡復活：暫不考慮

## 3. 錄製與召喚的關係 — 主題契合度與實作分析

*分析日期：2026-05-02*
*對應設計：[`設計構想.md`](設計構想.md) 第三節 1（錄製期間的世界狀態子節）*

### 3.1 核心問題

錄製期間「**世界狀態**」如何處理？特別是：
- 已召喚的分身（active clone）怎麼辦？
- 它們造成的世界影響（按按鈕、擋投射物）保留還是消失？
- 玩家視覺上看到什麼？

這是**錄製機制**與**召喚機制**的交界——兩者怎麼共存決定了遊戲的解謎風格。

### 3.2 已確認的設計決策

| # | 決策 |
|---|---|
| 1 | 模型 A1：**模糊剪影 + 凍結 + 保留世界影響** |
| 2 | 已召喚分身視覺：30% 亮度、低飽和、模糊剪影（**不是完全隱藏**） |
| 3 | 已召喚分身物理：collision_layer 維持原值（被機關偵測），RecordingProxy 對其穿透 |
| 4 | 凍結期間世界事件「**繼續**」依分身的當下狀態（門正在開的繼續開） |
| 5 | 視覺過渡：淡入/淡出 0.3 秒 |

### 3.3 為什麼是「模糊剪影」而非「完全隱藏」

**完全隱藏的問題**：
- 分身仍影響世界（壓按鈕、擋投射物），玩家看不到分身會困惑「為什麼這個門開著」
- 世界邏輯與視覺脫鉤，玩家判斷靠記憶
- 體驗不直觀

**模糊剪影的優點**：
- 玩家仍看得到「**那邊有個什麼**」，理解世界狀態的來源
- 視覺上明顯區分於「活躍分身」（飽和、清楚）與「殘骸痕跡」（無物理、純視覺）
- 主題更貼合：「**它在那裡，但時間暫停**」

### 3.4 視覺規格

#### 凍結中分身的視覺處理

```gdscript
# 假設既有 Clone 視覺：modulate = Color(0.4, 0.7, 1.0, 0.7) (淡藍灰，70% alpha)

# 凍結時：
modulate = Color(0.5, 0.5, 0.5, 0.3)  # 灰色、30% alpha
# 加上 blur shader（可選）
material.set_shader_parameter("blur_amount", 2.0)
```

#### 視覺對比（錄製期間畫面上的所有元素）

| 對象 | Modulate | 飽和度 | 模糊 |
|---|---|---|---|
| 玩家本體（凍結） | 白、50% alpha | 中飽和 | 無 |
| RecordingProxy | 淡藍灰、100% alpha | 中飽和 | 無 |
| **凍結中分身（錄製期間）** | **灰、30% alpha** | **低飽和** | **輕微 blur** |
| 物理殘骸 | 中等淡色、100% alpha | 中飽和 | 無 |
| 新殘骸痕跡 | 50% alpha | 低飽和 | 無 |
| 舊殘骸痕跡 | 20% alpha | 極低 | 輕微 blur |
| 亮光點 | 飽和亮藍/亮白、脈動 | 高 | 無 |
| 痕跡光點 | 暗灰、25% alpha | 極低 | 無 |

凍結中分身與舊殘骸痕跡的關鍵差異：
- 凍結分身有清楚輪廓（仍是「人」形），舊痕跡只剩朦朧輪廓
- 凍結分身保留淺色調（仍可辨認），舊痕跡近乎黑白
- 凍結分身**有物理**（被按鈕偵測），舊痕跡**無物理**

### 3.5 實作架構

#### Clone.gd 加凍結機制

```gdscript
extends Player
class_name Clone

# ... 既有 input/recording 邏輯 ...

# === 凍結機制（錄製期間用）===
var _frozen_state: Dictionary = {}

func freeze():
    if _frozen_state.size() > 0:
        return  # 已凍結
    _frozen_state = {
        "physics_process": is_physics_processing(),
        "modulate": modulate,
    }
    set_physics_process(false)
    # 視覺：淡入到模糊剪影
    var tween = create_tween()
    tween.tween_property(self, "modulate", Color(0.5, 0.5, 0.5, 0.3), 0.3)
    # collision_layer 維持原值（A1：仍會被機關偵測）

func unfreeze():
    if _frozen_state.size() == 0:
        return
    set_physics_process(_frozen_state.physics_process)
    var tween = create_tween()
    tween.tween_property(self, "modulate", _frozen_state.modulate, 0.3)
    _frozen_state.clear()
```

#### RecordingProxy 對凍結分身穿透

```gdscript
# RecordingProxy.gd（extends Player）
func _ready():
    super._ready()
    # 排除分身層（layer 2）
    collision_mask = 1  # 只偵測 World，不偵測 Clone
```

#### PlayerController 的協調

```gdscript
extends Node
# autoload，管理錄製狀態與分身凍結

func start_recording(player: Player):
    # 凍結所有 active Clone
    for clone in get_tree().get_nodes_in_group("active_clone"):
        clone.freeze()
    # ... 其他錄製儀式 ...

func end_recording(player: Player):
    # 解凍
    for clone in get_tree().get_nodes_in_group("active_clone"):
        clone.unfreeze()
    # ... 其他結束儀式 ...
```

### 3.6 邊界情況的場景演練

#### 場景 1：分身踩按鈕、玩家錄製

- 召喚分身 A → A 走到按鈕 → 門開
- 按 R → A 凍結成模糊剪影、仍踩按鈕、門仍開
- RecordingProxy 走過開門
- 結束錄製 → A 解凍恢復、繼續播放剩餘錄製
- A 在凍結期間「沒走完」的部分繼續播

#### 場景 2：凍結期間 RecordingProxy 與凍結分身位置重疊

- A 凍結在位置 P
- RecordingProxy 走到 P
- 因 RecordingProxy.collision_mask 排除 layer 2，A 不擋 RecordingProxy
- 視覺上：玩家看到 RecordingProxy 與 A 的剪影重疊（半透明 + 半透明 = 更暗的模糊區域）

#### 場景 3：凍結期間 RecordingProxy 觸發機關

- 場景中有按鈕 X、A 凍結中、不在按鈕 X 上
- RecordingProxy 走到按鈕 X、按下 → 門開
- 結束錄製 → A 解凍繼續、A 不在 X、X 維持被 RecordingProxy 按
- ......但 RecordingProxy 已經消失了！誰按著 X？

**處理**：RecordingProxy 結束錄製就消失，**它造成的世界影響也消失**（按鈕釋放、門關上）。
跟「召喚分身播完消散」的邏輯一致——分身消失，它對世界的影響也消失。

世界回到「凍結瞬間 + 凍結分身的狀態」（不含 RecordingProxy 的影響）。

#### 場景 4：錄製中 RecordingProxy 死亡（A3）

- 凍結的分身 A 仍在原位
- RecordingProxy 撞 hazard 死於 P
- 形成物理殘骸於 P（屬於新錄製的槽位）
- 結束儀式啟動：分身 A 解凍恢復播放
- 物理殘骸留在 P（永久性，不受錄製結束影響）

#### 場景 5：凍結分身的「進行中事件」

- A 在錄製前 0.3 秒踩了按鈕，門 open_progress = 0.5（半開）
- 按 R → A 凍結
- 凍結期間：A 仍踩按鈕、按鈕仍按下、門繼續開向 1.0（**完全開**）
  - 注意：門邏輯運作在 `_physics_process`，按鈕的 signal 正常觸發，門照常開到底
- 錄製結束、A 解凍 → A 繼續走（可能離開按鈕）→ 門開始關
  
即：**「進行中事件」依分身的當下狀態自然演進**，不需特別處理。

#### 場景 6：多個分身重疊凍結

- A 在按鈕、B 也在按鈕（兩個都在）
- 按 R → 兩個都凍結
- 視覺：兩個剪影重疊（更模糊更不清楚）
- 物理：按鈕仍被偵測（雙倍偵測但不影響邏輯）
- 結束 → 兩個都解凍

#### 場景 7：凍結期間分身的播放進度

- A 召喚出來、播到第 50 frame、被凍結
- 凍結期間：current_frame 不增加
- 解凍：從第 50 frame 繼續播
- A 不會「漏跳」幾秒的動作

#### 場景 8：投射物與凍結分身

- 機關發射投射物，路徑上有凍結的 A
- A 仍擋投射物（A1：collision 仍生效）
- 投射物本身**不被凍結**（它是世界物件，不屬於 Clone）
- 玩家錄製 RecordingProxy 安全通過 A 後方
- 結束錄製 → A 解凍、A 繼續走（可能離開投射物路徑、玩家後續被打到）

### 3.7 實作難度評估

| 項目 | 難度 |
|---|---|
| Clone.freeze() / unfreeze() | ★★（中低） |
| 視覺淡入淡出 + 模糊 shader | ★★★（中，shader 要寫） |
| RecordingProxy collision_mask 設定 | ★（低） |

| **整體** | **★★★ 中等** |

### 3.8 主要風險

1. **凍結剪影的視覺與其他元素混淆**
   - 玩家可能分不清「凍結分身」「舊殘骸痕跡」「痕跡光點」
   - 緩解：原型階段先用色塊嚴格區分（凍結=灰色 30%、舊痕跡=接近黑白 20%、痕跡光點=暗灰光圈）
   - 中期試玩確認辨識度

2. **凍結時的「進行中事件」邏輯**：例如門正在開、投射物在飛
   - 投射物：飛行器物件本身不被凍結（它是世界物件）
   - 結論：投射物正常飛、可被凍結分身擋（A1 規則）

3. **RecordingProxy 世界影響的「消失時機」**：場景 3 提到的「RecordingProxy 消失後它按的按鈕釋放」
   - 跟「召喚分身消散」是同一邏輯，沿用既有處理

4. **大量分身同時凍結時的效能**：理論上 5 個分身同時凍結沒問題（只是 set_physics_process(false)），但若加 blur shader 在每個分身上可能影響效能
   - 緩解：原型階段不做 blur，只用 modulate 色調與透明度區分

### 3.9 已確認的設計決策清單（已寫入 設計構想.md）
